# Kamigo 1.0 integration contract

## Install

Use Ruby 4.0.6 and Rails 8.1.3.1. During development reference the sibling
kamigo, kamiflex and kamiliff repositories through Gemfile path dependencies.
Run `rails generate kamigo:install` and `rails db:migrate`. This installs
principal/external-identity and receipt/outbox migrations into the host database.
It does not expose a webhook or create authenticated sessions.

## Routing and rendering

```ruby
renderer = Kamigo::Rendering::Renderer.new(view_paths: Rails.root.join("app/views"))
class Greetings < Kamigo::Controller
  def hello
    render "greetings/hello", name: "friend"
  end
end
router = Kamigo::Router.new do
  command "hello", to: "greetings#hello"
end
dispatcher = Kamigo::Dispatcher.new(
  router: router,
  handlers: { "greetings#hello" => Greetings.action(:hello, renderer: renderer) },
  policy: ->(context, target, event) { !context.principal_id.nil? }
)
```

`app/views/greetings/hello.line.erb` and `.telegram.erb` can contain
`<% text "Hello #{@name}" %>`. A `.text.erb` file is a plain-text fallback.
LINE templates can use `line_flex` with the Kamiflex DSL; Telegram templates use
`telegram_message(text:, buttons:)`. Use structured messages, not interpolated JSON.
Each dispatch receives a fresh handler; each render receives a fresh view/builder.
Rules use declaration order; exact commands are indexed. Predicates must be pure,
bounded and side-effect free; authorization runs after route resolution.

Platform adapters can register another template suffix, a platform helper DSL and
the plain-text fallback without changing Kamigo core. For example:

```ruby
module SlackRenderHelpers
  def slack_blocks(text)
    emit(type: 'section', text: {type: 'mrkdwn', text: text})
  end
end
Kamigo::Rendering.register(:slack, helper: SlackRenderHelpers,
  fallback: ->(text) { {type: 'plain_text', text: text} })
```

The renderer will then resolve `hello.slack.erb` before `hello.text.erb`. The
adapter still owns signature verification, event normalization and delivery;
registering a renderer alone does not claim that a platform transport exists.

## Identity and authorization

Identity::Service separates internal principals from provider/scope/subject.
Only a trusted server-side verifier may produce VerifiedIdentity. Resolve is a
lookup, not authentication. The host must authenticate the current principal,
check link intent and CSRF, verify provider credentials, and provide an independent
login/recovery method before allowing removal of the final login identity.
Shared display names are never evidence that two accounts belong to one person.
Host policies deny by default; Kamigo provides generic conversation/membership
tables while the host owns product role rules and verified membership observation.
Kamiliff entry names do not prove group membership. Browser source/group fields
must never authorize warehouse access. See Kamiliff's own security contract.

## Delivery and persistence

Hosts with more than one account for the same platform configure one immutable
connection definition per account. Kamigo keeps the lookup interface independent
from the host's credential store:

```ruby
Kamigo.connections = Kamigo::Connections::Registry.new do |platform:, connection:|
  MyConnectionStore.resolve(platform:, connection:)
end

definition = Kamigo.connections.resolve(platform: :line, connection: "kamigo_0")
```

The resolver returns a `Kamigo::Connections::Definition` (or matching keyword
Hash) containing `platform`, `connection`, `identity_scope`, and a configured
platform `adapter`. An unknown name raises `UnknownConnection`; a resolver cannot
silently substitute another account. The host owns credential encryption,
enable/disable policy, default selection, and cache invalidation. A connection
identifies the bot account used for verification and delivery. `identity_scope`
identifies the provider subject namespace and may be shared only when the host has
trusted proof that two connections issue subjects in the same namespace.

LINE validates HMAC of exact raw request bytes; Telegram checks the webhook secret.
Pass only the configured server-side connection identifier to the adapter.
Reliability::Receiver verifies events, deduplicates provider IDs per connection,
and commits local handler mutations and Outbox together. Context resolution must
return a trusted Kamigo::Context. Keep network calls outside this transaction.
Create host-originated rows with `Outbox.enqueue!`; on PostgreSQL it serializes ID
allocation and commit for the same platform/connection/conversation with a
transaction advisory lock. Direct `create!` is only suitable for fixtures or a host
that provides an equivalent serialization guarantee.
Reliability::Delivery claims a pending row only after earlier pending/sending rows
for the same platform, connection and conversation have cleared, then calls the
configured platform transport and marks sent or uncertain. This keeps concurrent
workers from reordering one conversation. The migration materializes one
`stream_head` per active conversation and enforces it with partial indexes and check
constraints. `Delivery.ready_ids(limit:)` reads only pending heads, so its work is
bounded by the requested batch even when one stream has a million queued tails.
Hosts that need confirmed outbound history may pass `acknowledger:` to
`Reliability::Delivery`. It receives `outbox_id`, platform/connection/conversation,
the confirmed messages, their zero-based `message_indexes`, and the provider
receipt. LINE acknowledges its atomic batch after one successful response;
Telegram acknowledges each message immediately after its own successful response,
so a later failure does not erase knowledge of an earlier success. Existing custom
adapters that return successfully without yielding acknowledgements fall back to
one acknowledgement for all messages. A host must persist callbacks idempotently,
using outbox ID plus message index; callback failure makes the outbox uncertain and
must never trigger a blind resend.
Hosts must run the bounded `recover_stale_sending!`, `expire_stale_pending!`, and
`delete_stale_terminal!` maintenance APIs on an explicit cadence.
Network ambiguity is not automatically retried. An uncertain head advances for
availability; absolute ordering against a provider that accepts after an ambiguous
timeout requires provider reconciliation before later messages are released.
A worker, reconciliation policy, receipt expiry, outbox/token retention and alerting
must be implemented by the host before production. LINE reply tokens are short-lived;
schedule promptly and never silently convert an expired reply to a paid push.
HttpTransport uses fixed HTTPS endpoints, bounded timeouts/body sizes and sanitized
errors. No live platform delivery has been exercised during local acceptance.

## Scope and release gates

Agent is a bounded provider interface and cannot run inside an ActiveRecord transaction;
async Agent dispatch and human handoff remain reserved extension points. Product
login, role rules, inventory, billing and migration belong to the host application.
The generic render registry supports a Slack-style DSL, but a real Slack adapter is
only present when the host supplies and tests its verifier/normalizer/transport.
JSON is pinned below 3: Rails 8.1.3.1 JSON.decode currently passes a positional options
hash incompatible with JSON 3.0.1 under Ruby 4. Re-evaluate when upstream is compatible.
## 可執行驗收

`script/acceptance/host_install.rb` 會建立一次性 Rails 8.1 專案，執行 `kamigo:install`、全部 migration 並實際啟動宿主。`script/acceptance/postgres_host_install.rb` 對全新 PostgreSQL 15 宿主執行同一 generator 與六支 migration，並驗證模型、foreign key、check constraint 與七個 outbox partial index。`script/acceptance/postgres_reliability.rb` 另以一次性 PostgreSQL 驗證並行收發、未提交交易順序、三類 maintenance，以及單一 stream 一百萬筆 tail 的 ready index 計畫。三者都只使用暫存目錄並在結束時清理。
